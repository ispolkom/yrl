# YRL roadmap

This file distinguishes the **accepted implementation-stage sequence** from the older long-term product plan in `docs/DESIGN.md` §10. It records the state after the initial corrective work in implementation Stage 5. Stage numbers in these two plans are separate; completing a security stage does not imply that an aspirational desktop, transport or cross-platform milestone is complete.

## Accepted implementation stages, in order

| Stage | Scope | State |
|---|---|---|
| **0. Resilient remote-access transport** | One connection manager selects configured direct UDP, direct TCP and TCP relay routes. Failover preserves a live session, operations and confirmed data through RESUME, with bounded resources and interactive priority. | Implemented and accepted. Focused route tests cover UDP → TCP and direct TCP → relay during file transfer. |
| **1. Independent Client ↔ Executor cryptographic authority** | An inner pinned Noise IK channel authenticates the client to Executor, protects authoritative ACK/SEQ and operations from Gatekeeper, and places password/rights checks inside Executor. | Implemented and accepted; G14/G15 are active regression tests. |
| **2. Authority refresh and revocation** | Device-key removal, account disablement and rights changes end affected live sessions and prevent their RESUME, including active PTY, commands, files and tunnels. | Implemented and accepted; focused tests in `tests/revocation.rs`. |
| **3. Component isolation** | Gatekeeper, Executor, Broker, Audit and Firewall have separate privileges and filesystem policies; seccomp covers all threads; user children join a per-session cgroup before execution and are killed with that session. | Implemented; deployment acceptance remains in `STAGE3_ACCEPTANCE.md`. |
| **4. Key and secret lifecycle** | Protect role-private key files, clear secret buffers, support unattended services, offline encrypted recovery, safe Noise-key rotation, device revocation and protected migration. | Implemented in **`f69e4b7`**; deployment acceptance and the Audit journal-signing rollover limit are in `STAGE4_ACCEPTANCE.md`. |
| **5. Failure and overload resilience** | Find and remove failure modes exposed by sustained load, repeated disconnects and bounded-resource operation without weakening authentication, cryptography or delivery guarantees. | Implemented through 5.1–5.6; isolated fault-injection and installed-host acceptance remain open in Stage 8. |
| **6. Trusted audit and software delivery** | Rotated and independently verifiable Audit history, signing-key lifecycle, signed releases and downgrade-safe updates. | Implemented through substages 6.1–6.6. | **7. Extended cryptographic protection** | Versioned profiles, hybrid post-quantum transport/signatures, OPAQUE, FIDO2 and optional TPM-backed key handling. | Implemented through 7.1–7.6 behind default-off feature gates. | **8. Final acceptance** | Regression, installed-runtime security, fault injection, crypto, performance and final report. | Conditional acceptance. The Debian lab covered installed operation, signed updates, hybrid proof paths and resource limits. Physical hardware, long-duration workloads and residual fault cases remain open. See `STAGE8_ACCEPTANCE.md`. |

## Stage 8 acceptance in progress

Acceptance evidence and blockers are tracked in `STAGE8_ACCEPTANCE.md`. Stage 7 features remain default-off.

## Stage 7: extended cryptographic protection

### Substage 7.1: authenticated cryptographic profiles

YRL now has a canonical, bounded profile offer and selection protocol. Profile IDs unambiguously name the complete Noise pattern, authentication, KDF and AEAD suite. The exact offer digest, selected ID and role context are carried inside the Noise handshake payload and the context is also in the Noise prologue, so stripping, substitution, replay across Gatekeeper/Executor roles and unauthenticated negotiation are rejected. Unknown, repeated and policy-forbidden IDs fail closed; a route failure never triggers a weaker offer.

The client keeps separate persistent profile high-water marks for each pinned peer key and Gatekeeper/Executor context. Both a configured minimum and the remembered value are enforced on every fresh route handshake, including RESUME. The state is atomically written to a private file. Gatekeeper and Executor remain independent handshakes; transport selection does not select a crypto profile. `YRL_CRYPTO_MIN_PROFILE` configures the minimum accepted ID.

The only registered suite at this point is `0x00010001`, the existing Noise IK / X25519 / ChaChaPoly / BLAKE2s construction. Negotiation is compiled only with the default-off `crypto-profiles` feature, preserving the installed wire format until Stage 8 validates migration. There is deliberately no opportunistic legacy fallback. Focused tests cover malformed, unknown, repeated, stripped and substituted profiles, role separation and persistent monotonic state; they are prepared but not run.

### Substage 7.2: hybrid post-quantum transport

Implemented as default-off profile `0x00020001`. The existing authenticated Noise IK is the outer layer and negotiates the profile; a Clatter Noise `pqNN` exchange with RustCrypto ML-KEM-768 then runs encrypted inside it. The outer handshake hash is domain-separated and mixed into the PQ key schedule, following Clatter's documented hybrid dual-layer construction. Application frames use the resulting PQ transport state; ML-KEM is handshake-only.

This preserves classical X25519 security, role/pinned-key separation, ACK/SEQ, RESUME and every transport. Expensive PQ work starts only after the classical device key is authorized. `YRL_CRYPTO_ENABLE_EXPERIMENTAL_PQ=1` is required on both sides and the feature is disabled by default pending Stage 8 vectors/interoperability/performance/review. Focused compile-only tests cover profile refusal without the feature and a complete bound ML-KEM-768 upgrade.

### Substage 7.3: OPAQUE password authentication

Implemented behind the default-off `opaque-rfc9807` feature with `opaque-ke` 4.0.1's RFC 9807 Ristretto255/SHA-512/Argon2id suite. Registration is performed only inside an already authenticated Executor session, so the new password remains client-side; server setup and per-account records use private, bounded, atomic storage. KE1/KE2/KE3 are bounded and tied to account, authenticated device key, Executor role, negotiated profile and Noise transcript. Unknown accounts use the library's fake-record path and the existing throttles remain in force.

OPAQUE login is explicit (`YRL_AUTH_OPAQUE=1`) and never falls back to legacy LOGIN. `yrld opaque-init` explicitly creates server state and `yrl opaque-register` migrates after one successful legacy authentication. Production enablement and RFC-vector execution remain Stage 8 work. The dependency's historical audit predates this exact release, so compilation is not claimed as cryptographic validation. Broker ROOT OPAQUE is not enabled: its independent operation-bound design remains a documented integration boundary, and existing Broker step-up is unchanged.

### Substage 7.4: hybrid post-quantum signatures

Implemented behind default-off `hybrid-signatures` with RustCrypto `ml-dsa` 0.1.2 (FIPS 204 ML-DSA-65) and the existing Ed25519 implementation. The bounded `YHP1` public-key and `YHS1` signature formats bind profile, purpose, generation, both public keys, derived key ID and a length-delimited message. Verification has only AND semantics: malformed, truncated, stripped, cross-purpose, cross-generation or single-valid-member envelopes are rejected.

Purposes independently cover device/server identity, handshake proof, Audit entries/checkpoints/deletions, release root/delegates, transitions and recovery. The required hybrid handshake binds pinned key pairs to both X25519 identities, role, profile and Noise transcript. Password step-up also uses mutual hybrid proofs in the independent Executor and Broker XK handshakes. Audit and release verification use the profile of their trusted keys. Owner-driven key files are purpose-separated, bounded and zeroized; planned transitions require old and new hybrid signatures, while emergency transitions require a separately pre-trusted recovery key. `yrl-release hybrid-*` provides offline generation/sign/verification without embedding production keys. Historical Ed25519 objects remain explicitly classical. Production activation waits for Stage 8 because the exact RustCrypto release is unaudited.

### Substage 7.5: FIDO2 hardware confirmation

Implemented behind the default-off `fido2` feature using `fido2-rs` and Yubico libfido2. The native CLI talks CTAP2 directly, forces FIDO2 (no U2F downgrade), creates ES256 credentials, and requests user presence plus configurable user verification/PIN. The relying-party identifier is a stable administrator-configured DNS-style name (`YRL_FIDO2_RP_ID`); both peers must agree on it and on the UV policy.

Persistent bounded one-use challenges bind account, device key, role/channel and, for step-up, the exact level, operation parameters, request and Broker identity. Server verification checks RP hash, UP/UV, ES256 signature and monotonic counters. Credentials are account/device-bound, support multiple tokens and audited administrative import/revocation. Executor owns login/SUDO records; Broker independently owns ROOT records. Once a relevant credential exists, failed token/PIN/UV verification never falls back to password or OPAQUE. Physical-token interoperability and recovery drills remain Stage 8 acceptance; FIDO2 is classical, not post-quantum.

### Substage 7.6: TPM 2.0 key protection

Implemented behind the default-off `tpm2` feature using stable `tss-esapi` 7.7 and TPM2-TSS. `device`, `swtpm` and other standard TCTIs are selected explicitly. YRL can seal arbitrary bounded software secrets with a TPM-protected XChaCha20-Poly1305 wrapping key, load Noise keys through that backend, and generate/sign with TPM-native non-exportable P-256 keys for explicitly compatible purposes. Sealed X25519, Ed25519, ML-KEM and ML-DSA material is still software cryptography after unseal and is never labelled hardware execution.

Optional PCR binding is exact and fail-closed. Required policy also requires a dedicated owner-authorized TPM NV counter; blob generations must match it, and planned Noise-key rotation uses a durable pending blob before incrementing the counter so startup can finish an interrupted commit without rollback. Required policy never uses a plaintext key when the TPM/blob/PCR/counter is unavailable. Explicit migration and recovery-export commands, per-role NV-index requirements and motherboard/TPM/OS replacement procedures are documented. Software-only operation remains unchanged when policy is off. swtpm and physical-hardware tests are prepared but intentionally deferred to Stage 8; no TPM, PCR, NV or firmware state on this host was touched.

## Current Stage 5: Failure and overload resilience

The initial Stage 5 investigation traced both the 5.9 MiB/s throughput regression and a missing final upload confirmation to one cause: Stage 4 wrapped every encoded Noise plaintext frame in `Zeroizing`, so an unoptimized build performed a costly volatile wipe for every 60 KiB bulk frame. Link already retains the same bulk payload until its authoritative ACK, so wiping that additional encoded copy did not shorten the payload's lifetime. Restricting this extra wipe to the LOGIN frame restored 70 MiB/s upload and 62 MiB/s download on the same host; Noise authentication, rekeying, pinned identities, ACK/SEQ and bounded Link retention are unchanged.

Sensitive control data retains explicit lifecycle handling. The CLI input and decoded server password use `Zeroizing`; LOGIN payloads and their temporary Noise plaintext encodings are cleared; failed Noise opens clear their output buffer. A CLI step-up phrase is held in a zeroizing caller buffer, travels inside the independent Noise XK proof, and is cleared by Executor or Broker after denial or verifier use. `STEPUP_PROOF` in the ordinary session contains the inner Noise ciphertext, not the phrase.

The original failing 48 MiB chaos upload now completes in about 1.7 seconds through repeated connection cuts with the existing 15-second confirmation deadline. The final FILE_END response was delayed by the same throughput regression; no loss, duplication, ACK/SEQ fault or command replay was found. The Audit unsafe-key test now asserts rejection of a mode-0644 signing key without depending on an obsolete error string.

### Substage 5.1: global resource admission

Executor now shares one configurable resource manager across all of its sessions. Link charges the exact encoded bytes retained until ACK against global, device-key and account budgets (defaults: 256 MiB globally and 64 MiB per principal). Admission waits through the existing backpressure path; it does not drop frames or impose a transfer-rate limit. Global and per-principal pools retain a protected interactive reserve inside the same hard ceiling, while Link's existing per-session window and interactive-first scheduling remain in force.

Active EXEC, PTY, file-transfer, tunnel and filesystem operations retain their existing per-session limits and additionally acquire global, per-session, per-key, per-account and per-operation-type permits. The default aggregate ceiling is 256 active operations, with smaller principal and type shares. Session admission is now atomic and also limits sessions per account as well as globally and per key. RAII permits are released on normal completion, errors, session close, authorization revocation and task cancellation; closing a Link releases pending and unacknowledged memory immediately. `ResourceLimits` and `ServerConfig::set_resource_limits` provide explicit configuration with validation that every memory pool can carry one maximum legal frame.

Focused tests were added for hierarchical admission, release of all quota levels, the protected interactive reserve, and Link-memory release on ACK/close. They are intentionally not executed yet; comprehensive and repeated runs remain reserved for final Stage 5 acceptance.

### Substage 5.2: cgroup v2 and service resource containment

Every Executor session now configures its existing cgroup before any child can enter it. Safe defaults set `memory.high=1 GiB`, `memory.max=2 GiB`, `pids.max=512`, `memory.oom.group=1`, neutral `cpu.weight=100` and, when the controller is delegated, `io.weight=100`. `cpu.max` defaults to unlimited and `io.max` defaults to empty, so this substage does not introduce an arbitrary computation or file-transfer rate ceiling. Typed `SessionLimits` and `/etc/yrl/yrl.env` overrides support `memory.max`, `memory.high`, `pids.max`, `cpu.max`, `cpu.weight`, `io.weight`, and explicit per-device `io.max` rbps/wbps/riops/wiops controls. Invalid configurations and an explicitly requested `io.max` without a delegated IO controller fail cgroup creation rather than silently running a child outside the requested hard limits.

The cgroup object remains owned by the Executor session, not by a network connection, so route replacement and RESUME keep the same cgroup and counters. OOM grouping kills only the affected session's child processes; Executor monitors `memory.events` and `pids.events`, records limit events, reports OOM/process-limit failures to affected operations, and leaves neighboring sessions running. Normal completion, protocol failure, authorization revocation and grace expiry retain the existing `cgroup.kill` and empty-cgroup removal path.

Installed systemd services now have accounting, `MemoryHigh`, `MemoryMax`, `TasksMax`, CPU/I/O fair-share weights and explicit OOM policy. Executor's 4 GiB/8 GiB service envelope is deliberately above the 256 MiB Stage 5.1 Link budget and includes all delegated session children; its `OOMPolicy=continue` prevents a child OOM from stopping unrelated sessions. All services limit restart storms to five starts per 60 seconds. Focused cgroup configuration/event, unit-policy, RESUME-retention and neighbor-isolation tests were prepared but not executed; installed-host behavior remains part of final acceptance.

### Substage 5.3: IPC overload protection

Audit, Broker and Firewall now use the Executor admission pattern in two phases: a short-lived pre-authentication permit is bounded globally and per kernel peer UID, then an authenticated active permit is bounded globally and per Noise principal. Permits are RAII-owned by the connection task, so EOF, cancellation, authentication failure and every protocol/error return release both levels. Audit has separate per-source shares, preventing one reporting component from monopolizing its door; Broker and Firewall each have one authorized counterpart and retain hard global ceilings against its compromise. The typed service entry points accept reduced limits for deterministic overload tests.

All three doors bound handshake, read/idle and write waits according to channel purpose. Audit expires idle persistent reporters after 60 seconds and clients reconnect with the existing retry semantics. Broker permits 15 minutes of inactivity because its channel is session-scoped and normally quiet; expiry closes only the local pipe, while Executor keeps the user session alive, detects the closed pair and reconnects for a later ROOT begin or returns an explicit denial. Firewall accepts exactly one typed request per authenticated connection, matching its existing client and eliminating idle keep-alive retention. Its failure and overload paths still mean “not open”.

Audit background reporting is capped at 256 in-flight events; excess ordinary events increment the existing degradation counter instead of creating unbounded tasks. Mandatory events use a distinct connection lane, retain bounded connect/read/write waits and bypass the ordinary backlog. Journal append work is admitted before it reaches the blocking pool and an ACK is sent only after append completion; critical callers therefore remain fail-closed rather than treating overload as success. Broker's existing 64-frame pipe and StepServer pending bound remain in force, and Firewall has no application request queue. Focused admission/RAII/fair-share and Audit queue/critical-lane tests are prepared but intentionally not executed.

### Substage 5.4: network fairness and load management

Reliable UDP now paces new data after its first RTT sample instead of releasing the entire congestion window in one burst. Each RTT is divided into 16 bounded send slices; the slice size comes from the effective congestion/peer window, so loss-driven `cwnd` reduction immediately reduces the burst and ACK growth restores capacity. Retransmission, SACK, RTO, receiver-window and mute behavior are unchanged. Startup retains the existing small initial burst, and low-RTT clean paths have no fixed rate ceiling.

The authenticated side now admits attached network transports globally and by device key and account (defaults 256/32/32; principal shares deliberately allow one replacement route alongside each default session share). A work-conserving fair scheduler rotates 16 KiB write/processing quanta between active session flows; it has no clock or token rate, so a lone session acquires every turn immediately. Link's existing interactive-first queues and memory reserve now extend to the shared scheduler. Only `FILE_DATA` is bulk: transfer setup, completion and abort, ACK/SEQ, keepalive, terminal and step-up traffic use the protected control lane. The scheduler permits and connection quotas are RAII-owned by the attached transport and release on EOF, route replacement, cancellation and error while the resumable session remains available. `YRL_NETWORK_CONNECTIONS_TOTAL`, `YRL_NETWORK_CONNECTIONS_PER_KEY`, `YRL_NETWORK_CONNECTIONS_PER_ACCOUNT` and `YRL_NETWORK_QUANTUM_BYTES` provide validated overrides.

Relay now separately limits active joined pairs globally and per observed socket IP (defaults 4096 and 64), and reserves two copy buffers from a 256 MiB global pool before joining a pair. A shared work-conserving scheduler rotates 16 KiB chunks between opaque pairs without inspecting ciphertext or imposing a rate when uncontended. The existing optional lifetime byte cap remains an explicit per-pair budget. Rendezvous IDs are used only to meet sockets and never as identity or a quota principal. Pair, buffer and observed-IP counters are RAII-released when either pump ends or the join task is cancelled. Validated `YRL_RELAY_*` environment overrides cover active-pair, buffer, quantum and optional per-pair byte budgets.

Focused compile-only tests cover pacing dependence on RTT/cwnd, uncontended fast-path and round-robin/control priority, hierarchical authenticated connection quotas, and Relay active-pair refusal/release by observed IP. They are prepared but intentionally not executed. Noise, Link ACK/SEQ, RESUME and route fallback are above or outside these schedulers and remain unchanged.

### Substage 5.5: disk resource management

Executor now owns a persistent, process-wide ledger of managed `FILE_PUT` reservations. Before a helper can create or extend a partial, the full announced final size is atomically admitted against global, authenticated device-key and account budgets (defaults 64 GiB / 16 GiB / 16 GiB). The same locked decision also preserves a configurable free-space floor (1 GiB by default), so parallel requests cannot all reserve the same available bytes. These are capacity reservations, not transfer-rate limits. `YRL_DISK_BYTES_TOTAL`, `YRL_DISK_BYTES_PER_KEY`, `YRL_DISK_BYTES_PER_ACCOUNT`, `YRL_DISK_FREE_RESERVE` and `YRL_PARTIAL_TTL_SECS` are validated Executor-side overrides.

Each managed `<target>.yrl-part` carries a random reservation xattr. The account-identity helper opens it with `O_NOFOLLOW`, requires a regular file owned by the target uid with exactly one hard link, and resumes it only when its tag matches the persistent ledger. BLAKE3 verification and the final same-filesystem rename remain unchanged; the tag is removed only after that rename. Legacy or unrelated untagged partials are refused and never deleted. The ledger is published atomically and reloaded after Executor restart, so an interrupted managed partial continues consuming its original quotas and the exact principal/path/size can resume without a second charge.

An in-memory active set prevents TTL cleanup from touching a live upload. Inactive tagged partials expire after seven days by default; cleanup rechecks `O_NOFOLLOW`, regular-file type, uid, one-link status and the random tag before deleting only the `.yrl-part` name. Success, explicit abort, session expiry, authorization revocation and operation failure release through one RAII reservation; cancellation removes the matching partial, while a route break retains the live task and reservation for RESUME. Quota exhaustion and ENOSPC/EDQUOT are distinct protocol errors. Ledger-write failure remains charged in memory and on disk rather than permitting double accounting.

This capacity accounting deliberately covers only YRL's managed `FILE_PUT` protocol. An arbitrary process launched by EXEC or PTY runs as the account's OS identity and may write through any filesystem access that identity already has; neither an application ledger nor cgroup `io.max` can impose a storage-capacity quota on those writes. Deployments needing that boundary must place account data on a filesystem with enforced user/project quotas (or an equivalently isolated volume). Such processes can also manipulate names owned by the same OS identity, so the helper still treats symlink/hardlink/tag mismatches as unsafe rather than claiming isolation from that identity.

Focused tests were prepared for atomic global/key/account admission and single-release behavior, fail-before-open free-space refusal, persistent restart/resume accounting, TTL cleanup versus active reservations, tagged cancellation cleanup, and symlink/hardlink refusal. The tests themselves were intentionally not run. Audit journal rotation remains Stage 6.

### Substage 5.6: component crash and restart resilience

Executor now persists a bounded operation journal under its own state directory. An EXEC or typed ROOT operation is bound to the authenticated device key, account, request identifier, kind and BLAKE3 request digest. `ACCEPTED` is durably published before execution and before the acceptance response; `RUNNING` follows before the side effect. A terminal result is retained until the authenticated client acknowledges it. After acknowledgement, a compact tombstone remains, so an old identifier can never become executable merely because its detailed result was discarded. The configured record ceiling defaults to 100,000; reaching it fails new admission closed instead of deleting replay protection.

On Executor startup, every persisted `ACCEPTED` or `RUNNING` record becomes `UNKNOWN`; neither arbitrary EXEC nor ROOT is automatically repeated. A reauthenticated client can query a result only with the same device key and account. `COMPLETED`, `FAILED`, `UNKNOWN` and acknowledged tombstones are explicit states. The client exposes stable request identifiers for callers that need post-reconnect status discovery. Failure of the Executor itself destroys its sessions and completes all pending client waiters with `SESSION_LOST`; a PTY and unknowable external side effects are not claimed recoverable.

Gatekeeper restart leaves Executor-owned sessions, cgroups, Link state and the RESUME grace window intact. Audit startup retains its existing verified-chain refusal, Firewall installs the closed baseline before announcing readiness, and an unavailable Broker converts proof-submitted operations to `UNKNOWN` while pre-execution failures are definite failures. Resource permits are process-local RAII state and disappear with the dead Executor; delegated children are killed by the service cgroup. The persistent disk ledger is reloaded and reconciles managed-upload reservations independently.

All five installed services now use `Type=notify` and a 30-second systemd watchdog while retaining the existing five-starts-per-60-seconds crash-loop limit. Recoverable component relationships use `Wants`, not failure-propagating `Requires`; authorization and critical Audit/Firewall paths remain fail-closed. Focused compile-only tests cover journal crash transitions, result acknowledgement and replay tombstones, explicit completion of pending client operations with `SESSION_LOST`, watchdog notification encoding and installed-unit policy. `cargo check -p yrl --all-targets` passes; the tests were intentionally not run. Installed crash/recovery behavior remains part of final acceptance.

The comprehensive workspace run, installed-service checks, real nftables and recovery on another host are reserved for final acceptance. Do not lower performance requirements or extend operation deadlines to mask overload or liveness defects.

Private Discovery is deferred and is not part of Stage 5. Multipath, route racing, NAT hole punching, UDP relay, GUI/desktop, other operating systems and YANDI NODE changes also remain outside this stage.

## Current Stage 6: trusted audit and software delivery

### Substage 6.1: Audit rotation and bounded retention

Audit keeps the existing record/checkpoint format and rotates each active journal into monotonically numbered segments. A signed segment envelope binds the journal name, generation, start/end times, record count, final sequence/hash, complete file hash and previous signed segment digest. The old segment is checkpointed before a crash-safe pending-seal/rename transaction; startup completes an interrupted transaction rather than creating a new chain. Active-state files are signed and published atomically.

Rotation defaults to 64 MiB or 24 hours, with a 4 GiB Audit-directory ceiling, 64 retained segments and a 256 MiB free-space reserve. Environment overrides are validated. Retention never silently removes history: a signed deletion witness containing the removed generation and hashes is synced before an archive is unlinked, and at least two recent archives are retained. Unsafe links are refused. If rotation, pruning or the storage reserve cannot complete, the service marks the journal broken and rejects further events, preserving fail-closed behavior for mandatory records. Focused rotation, signed-boundary and deletion-witness tests are prepared but not run.

### Substage 6.2: tamper, deletion and rollback evidence

Audit startup and `yrld audit verify` now verify every retained segment, its record/hash/sequence chain, signed head and signed segment envelope; generations must be continuous from zero to the signed active state. A missing generation is accepted only when the append-only deletion ledger contains a valid signed witness for exactly that journal/generation. File replacement, reordering, detached active state, an invalid witness and an unrecorded missing archive refuse startup rather than resetting the chain.

`yrld audit anchor <state-dir> <new-file>` obtains a freshly sealed checkpoint over the authenticated owner-to-Audit Noise IPC channel. The portable signed anchor binds both journals' generation, sequence and hash plus the signing public key. `yrld audit verify <state-dir> [trusted-anchor]` proves that retained history extends the supplied point and rejects rollback or key substitution. The anchor can be copied to a client or independent trusted node; no external service is mandatory. Without such an independently retained anchor, a host root able to restore or destroy the complete journal, key and local metadata can make a full local rollback indistinguishable from the restored state. Focused missing-segment and external-anchor rollback tests are prepared but not run.

### Substage 6.3: independent verification and export

The separate `yrl-audit` binary verifies a stopped server directory or exported snapshot using only public keys and signed metadata. `verify <dir> [trusted-anchor]` checks records, hashes, ordering, checkpoints, segment envelopes, deletion witnesses and an optional external anchor. Exit status is stable: 0 complete, 2 cryptographically valid but partial because retention removed segments, 3 damaged, 4 unverifiable, and 64 command or operational misuse. It never opens `sign.key` and needs no running YRL service.

`yrl-audit export <state-dir> <new-dir>` copies only regular, single-link public Audit material and emits an NDJSON event stream plus the raw verifiable chain. It excludes the signing key, locks, sockets and transaction files. Existing Audit fields contain account/operation metadata and hashed sensitive targets, never passwords, authentication secrets, commands, file contents or command output. The exporter retries a racing live snapshot instead of locking the journal. Once the copy independently verifies, the authenticated owner Noise channel asks Audit to sign the exact manifest digest; copying never occupies the mandatory event lane. The destination is private and must not exist, and access still requires both filesystem permission and the owner IPC identity. Focused public-only verification and domain-separated manifest-signature tests are prepared but not run.

### Substage 6.4: Audit signing-key lifecycle

Audit Ed25519 signing keys now have monotonic generations rooted in `audit/root.pub`; they remain independent of every Noise, device and release role. Planned offline rotation first requires the Stage 4 encrypted backup, seals and rotates both active journals, and writes a transition cross-signed by the old and new keys, including the new-key possession proof. Historical public keys and transitions are retained, while the private file is atomically replaced and sensitive seed/text buffers are zeroized. Startup validates the complete transition chain and reconciles only a private key already authorized by that chain.

An administrator can pre-register a separately generated offline recovery public key, again only after encrypted backup. Emergency rotation requires possession of its private seed: the new key and recovery key sign the transition, old active tails are preserved as explicit orphan evidence, and signed gap/deletion witnesses make verification partial rather than falsely complete. The prior generation is revoked. Normal revocation is signed by the then-current generation and records only a hash of the reason. Offline verification retains cryptographic verification of historical material but reports periods signed by a revoked/compromised key as partial, never as presently trusted merely because their signatures validate. Backup restore now validates the key-transition and complete segment chains. Focused planned cross-signing, historical verification, recovery possession and revocation tests are prepared but not run.

### Substage 6.5: signed YRL releases

The separate `yrl-release` tool implements an Ed25519 offline root, cross-signed root generations, bounded delegated signing keys and root-signed delegate revocation. No production key is embedded or generated by the build. A canonical manifest binds a monotonic release number, version, platform, architecture, persistent-data compatibility range, creation/expiry times, delegation generation and the exact sorted set of artifact paths, sizes and BLAKE3 hashes. Verification begins from a separately installed trust directory and rejects substituted, extra, absent, expired, revoked, out-of-scope or mixed-release components; GitHub/HTTPS/CDN provenance is never sufficient by itself.

`deploy/build-release.sh` builds all binaries with the locked dependency graph and emits source/toolchain provenance before manifest creation. `docs/RELEASES.md` documents offline root generation, initial fingerprint installation, delegation, signing, verification, rotation/revocation and publication. Provenance is recorded, but reproducible builds are not claimed until independent builders actually reproduce identical hashes. Focused complete-set, tamper, expiry and revocation tests are prepared but not run.

### Substage 6.6: downgrade-safe transactional updates

`yrl-update` verifies the entire signed bundle before staging it under `/opt/yrl/releases/<number>`. A private, no-follow persistent ledger stores the maximum trusted release, current/previous release, time floor, metadata-expiry high water mark and data format. Release numbers never move backward; controlled rollback changes only the atomic `current` directory pointer and leaves the maximum intact. Extra/missing/mixed artifacts, expired or replayed metadata, a backward clock jump and unknown state migrations are refused. Time-based freeze detection remains bounded by trust in the host clock and cannot detect a distribution server that withholds updates while also controlling that clock.

Staging, fsync, fixed-argument pre/post health checks, transaction publication, whole-release pointer replacement and ledger commit form the crash recovery protocol. `recover` completes a verified published/staged transaction or quarantines an incomplete stage; it never executes package scripts. The current persistent format is 1 and releases requiring another target are refused until a reviewed built-in crash-safe migration exists. Keys, configuration, authority, Audit data, disk reservations and the operation journal remain outside release directories.

Prepare/activate/failure/rollback are mandatory authenticated Audit events. Audit failure rolls activation back. The static `yrl-update.service` has no network access, capabilities, timer or `[Install]` section and can write only `/opt/yrl` and `/var/lib/yrl-update`; automatic installation is off. It does not restart services or expose arbitrary ROOT execution. `docs/UPDATES.md` documents online/offline manual operation and rollback boundaries. Focused ledger, symlink refusal, atomic pointer, signed-release and unit-policy tests are prepared but not run.
