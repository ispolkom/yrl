# YRL cryptographic profiles

This document records the specification status, threat boundary and dependency decision for Stage 7 mechanisms. A profile is not production-supported merely because its primitive exists in a library. The full authenticated composition, transcript binding, resource limits, migration and negative tests must also be reviewable.

## 7.2 X25519 + ML-KEM-768 transport assessment

ML-KEM-768 itself is standardized by [NIST FIPS 203](https://csrc.nist.gov/pubs/fips/203/final). RustCrypto `ml-kem` 0.3.4 is a plausible Apache-2.0/MIT implementation candidate, but it implements the primitive rather than a YRL/Noise hybrid handshake.

The candidate general-purpose X25519 + ML-KEM-768 combiner is [X-Wing draft 11](https://datatracker.ietf.org/doc/draft-connolly-cfrg-xwing-kem/). As of 2026-11-26 it remains an individual Internet-Draft with no RFC status and explicitly says it is work in progress. The available `x-wing` crate targets obsolete draft 06, while `rxwing` 0.1.0 targets draft 11 and has not established the maturity needed for an obligatory YRL production profile.

Noise revision 34 specifies DH patterns and PSK mixing, but no ML-KEM or X-Wing token and no reviewed mapping of this KEM exchange into authenticated Noise IK. Treating a KEM result as an application-chosen Noise PSK would require YRL to select token placement, ciphertext ordering, failure semantics, transcript/domain binding and key-erasure rules. That would be a new project-specific cryptographic construction, which Stage 7 explicitly forbids.

The blocker is resolved with a default-off compound construction based on Clatter 2.3's documented `HybridDualLayerHandshake`: the existing authenticated Noise IK completes first, negotiates profile `0x00020001`, and provides its handshake hash. A Noise `pqNN` exchange using RustCrypto ML-KEM-768 then runs inside the outer transport; domain-separated `MixHash` and `MixKeyAndHash` bind the outer transcript into the PQ symmetric state. Only the inner PQ transport keys protect application frames. This preserves the classical X25519 authentication and confidentiality even if ML-KEM fails, while adding ML-KEM forward secrecy against record-now/decrypt-later attacks.

I2P's released NTCP2 hybrid uses the more tightly interleaved Noise HFS `e1/ekem1` construction. YRL's compound construction has two extra encrypted messages but follows the same principles: ephemeral ML-KEM, authenticated/encrypted KEM material, transcript binding, and no PQ work per data frame. PQ work occurs only after the outer device key is authenticated and admitted, bounding anonymous computational DoS. Clatter is MIT; RustCrypto ML-KEM is Apache-2.0/MIT. Both are license-compatible. Clatter is not formally audited and currently selects `ml-kem` 0.2.x, so the feature remains experimental and disabled by default pending Stage 8 vectors, interoperability, performance and independent review.

## 7.3 OPAQUE implementation

[RFC 9807](https://www.rfc-editor.org/rfc/rfc9807.html) is implemented with stable `opaque-ke` 4.0.1 (MIT/Apache-2.0), Ristretto255/SHA-512/Argon2id. Its published historical audit covered an older release, so Stage 8 must execute official vectors and independently review this exact integration; a successful build is not such validation.

YRL therefore uses separate bounded KE1/KE2/KE3 frames. The context includes canonical length-delimited account, authenticated device key, Executor role, selected crypto profile and transcript binding. Unknown users take the library fake-record path. Setup and records are bounded 0600 single-link files with no-follow reads and atomic directory-synced replacement. Registration/password change occurs inside an already authenticated session and never sends the password. A failed OPAQUE attempt never falls back to Argon2 LOGIN.

ROOT step-up needs a separate Broker-owned OPAQUE server configuration and record/secret lifecycle, with the OPAQUE context bound to the one-shot operation digest and Executor/Broker identities. Reusing an Executor login PAKE session would destroy Broker independence. The ROOT password must still never enter Executor.

The feature is default-off and production activation waits for Stage 8. Passwords, export/session keys and temporary messages are not logged and sensitive buffers are cleared. OPAQUE reduces precomputation risk but does not eliminate guessing risk after complete server-state compromise. Existing lifecycle backup must include the `opaque` directory; losing setup makes records unrecoverable and the service fails closed rather than regenerating it.

## 7.4 Ed25519 + ML-DSA-65 signature profile

ML-DSA is standardized by [NIST FIPS 204](https://csrc.nist.gov/pubs/fips/204/final). YRL uses RustCrypto `ml-dsa` 0.1.2 under Apache-2.0/MIT with zeroization. It is an early, explicitly unaudited release, so the feature is default-off and requires Stage 8 official-vector and independent integration review before production activation.

A versioned `YHP1` key envelope binds purpose, generation, Ed25519 and ML-DSA-65 keys to one BLAKE3-derived key ID. The fixed-size `YHS1` signature envelope repeats that identity and contains exactly one 64-byte Ed25519 and one 3309-byte ML-DSA-65 signature over a canonical length-delimited TBS. Verification always checks both. Purpose identifiers cover device/server identity, handshakes, Audit records/checkpoints/deletion evidence, release roots/delegates, transitions and recovery, preventing cross-contour substitution.

Handshake helpers exchange the fixed envelopes through the already encrypted channel and sign both X25519 identities, initiator/responder role, selected profile and transcript binding. Hybrid public keys are caller-supplied pins; peer-supplied unpinned keys are never trusted. Planned rotation requires valid old and new hybrid signatures. Emergency replacement is domain-separated and requires a separately trusted Recovery-purpose key. Keys are generated only by an explicit owner CLI and never embedded. Existing Ed25519-only history remains verifiable only as classical profile data; it is not upgraded by attaching a new signature later.

## 7.5 FIDO2/CTAP2

The optional backend is `fido2-rs` 0.6 over Yubico libfido2 (BSD-2-Clause/MIT-compatible), not a YRL imitation of CTAP2. The client forces FIDO2, uses ES256, and requests user presence and configured user verification. Server-side verification independently checks the SHA-256 RP ID hash, UP/UV flags, DER ES256 signature and signature counter. PINs remain only in zeroizing client memory.

YRL is a native application, not a browser. `YRL_FIDO2_RP_ID` is therefore an administrator-provisioned stable DNS-style RP identifier, and the protocol uses bounded raw client data rather than asserting a WebAuthn browser origin. That client data is persisted as a one-use challenge bound to account and device-key hashes; login additionally binds the authenticated channel/profile, and ROOT binds the exact request, level, operation parameters and Broker public identity. Challenges are atomically burned before verification, so even invalid proofs cannot be replayed.

Registration is a physical-token ceremony that creates a private artifact; explicit audited administrative import binds it to the already authorized account and device key. Executor and Broker maintain separate private stores, multiple credentials are allowed, and revocation is audited. The recovery boundary is administrative re-registration through an existing authorized device; no cloud or manufacturer attestation service is trusted. Attestation is requested as `none`, so the claim is possession of the registered credential, not authenticator provenance. Enabling a credential makes its contour fail closed with no password/OPAQUE fallback. Zero counters are accepted for authenticators that do not implement them; a positive counter must increase. FIDO2 remains classical unless a future authenticator profile explicitly standardizes otherwise. Physical-device acceptance is deferred to Stage 8.

## 7.6 TPM 2.0 backend

The optional backend pins stable `tss-esapi` 7.7 (Apache-2.0) over TPM2-TSS (BSD-2-Clause). It uses standard ESAPI/TCTI calls and supports `device`, `swtpm`, `mssim` and other TCTIs understood by the library. The build host has no installed TPM2-TSS or simulator; compilation used isolated Debian 3.2 development/runtime packages. The prepared ignored test expects an isolated swtpm in Stage 8. No command in this development pass contacted or modified a TPM.

For current YRL algorithms, a TPM creates and seals a random 256-bit wrapping key. XChaCha20-Poly1305 encrypts the actual secret with authenticated purpose, generation, PCR list and TPM public/private-blob hashes. Unseal uses an encrypted ESAPI authorization session and returns zeroizing host memory. This is disk/device binding, not hardware execution of X25519, Ed25519, ML-KEM or ML-DSA. For protocols that explicitly allow it, the backend separately generates a TPM-native non-exportable NIST P-256 ECDSA key and signs SHA-256 digests without exporting private material; no existing identity/profile silently changes algorithm.

`off` never probes a TPM. `optional` uses a sealed blob when present and otherwise preserves software operation, but a present broken blob never falls back. `required` demands both the blob and a dedicated owner-authorized NV counter and fails closed. An owner authorization may be supplied only through a private hex file named by `YRL_TPM_OWNER_AUTH_FILE`; it is not accepted on a command line. An exact SHA-256 PCR policy may be configured for slots 0–23. NV generations prevent returning to an old blob. Rotation is a journaled sequence: durable next-generation blob, NV increment, verified unseal, atomic activation; startup resolves a pending blob based on the hardware counter. A counter must not be shared by independently rotated roles.

PCR binding can legitimately lock out a service after firmware, bootloader, kernel or policy changes. Before enabling it, keep the Stage 4 encrypted recovery package off-host. Plan the expected PCR transition before an update; if the old policy is already unavailable, restore the software secret only through the explicit recovery process, provision a new TPM/counter anchor and reauthorize the public identity. Motherboard/TPM replacement is the same trust-anchor replacement, not an automatic fallback. `YRL_TPM_ALLOW_RECOVERY_EXPORT=1` is required to write an unsealed recovery file. TCTI calls are synchronous and rely on the system TPM resource manager plus the existing systemd watchdog/crash-loop policy; a wedged device causes fail-closed restart rather than software fallback.

### Hybrid Audit signing

Build with `hybrid-signatures`. To provision a new Audit history, generate an Audit generation 0 pair with `yrl-release hybrid-keygen audit 0 STATE/audit/sign.key STATE/audit/sign.pub` before the Audit service first starts. Restore the installation's ownership and modes with the installer. Set `YRL_AUDIT_REQUIRE_HYBRID=1` in the Audit service environment to require the provisioned hybrid key at startup. Preserve and authenticate external anchors independently. Retain an existing classical Audit history as a separate historical record when provisioning a new root.

The service verifies both signatures when reopening a journal or rotating segments. The offline verifier and export paths use the same key type as the signed history. Planned rotation is signed by both key generations. The existing offline recovery and revocation commands accept hybrid keys. Generate a distinct `recovery` key and register the hex encoding of its complete public envelope in advance. Recovery of a lost key needs that previously registered key and an offline encrypted backup.

### Hybrid step-up proofs

A build with `hybrid-signatures` uses the Executor key store named by `YRL_HYBRID_EXECUTOR_KEYS` for password-based SUDO step-up. To require hybrid ROOT step-up, provision the same `local/` and `peers/` layout in a distinct Broker key store and set `YRL_HYBRID_BROKER_KEYS` on Broker and the client. These settings bind the signature requirement into the independent Noise XK handshake. Both roles verify Ed25519 and ML-DSA-65 over the operation-bound transcript. The configured mode refuses classical proofs. The classical wire frame limit continues to apply when the role has no hybrid policy.

The ROOT command takes the Broker pin as its positional authority key. Pass the independent Executor login pin with `--executor`. The SUDO positional pin can still supply the Executor login pin when omitted. FIDO2 assertions use the separate FIDO2 protocol and retain its existing policy.
